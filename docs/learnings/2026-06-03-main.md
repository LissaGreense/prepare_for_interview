# Team lead learnings — 2026-06-03 (quiz-app, branch main)

- Tasks created via TaskCreate BEFORE TeamCreate land in a different task list than the team's. After TeamCreate, both lead and teammates see the team's (empty) list, orphaning the pre-created tasks. Fix: create the team FIRST, then create tasks; or coordinate manually via briefs. (Two-way visibility gap surfaced by Luka on task #1.)
- Env is Python 3.14. FastAPI TestClient emits a StarletteDeprecationWarning about httpx — harmless, not our code.
- Good pattern (tracer): resolve questions/ dir from `Path(__file__).resolve().parents[N]`, never CWD — uvicorn may run from anywhere. Keep corpus root in one swappable constant + a `base=` loader param so tests can point at a fixture dir.
- Good pattern (tracer): verify CORS end-to-end via real uvicorn + `Origin:` header (curl), not just TestClient (TestClient doesn't exercise CORS middleware the same way).
- Frontend has no runtime validation lib (no Zod, by design — minimal personal tool). The `fetch().json() as Question[]` boundary cast is the accepted single un-validated seam. If hardening is ever wanted, that's the spot.
- Good pattern (#4): enforce `correct` in-range via a Pydantic `model_validator(mode="after")` on Question, so the out-of-range state is unrepresentable and folds into the same ValidationError skip path the loader already handles. Don't duplicate the check in the loader.
- Backend tests live in backend/.venv (Python 3.14). Run with `backend/.venv/bin/python -m pytest -q` from backend/. base python has no pytest.
- Scope note: #4's verification naturally produced #6's corpus/malformed/topics tests. #6 narrowed to /quiz randomization+count tests only — avoids overlapping AC. Watch for verification-tests bleeding into a dedicated test task; fold rather than duplicate.
- Dev-env gotcha: backend CORS is pinned to exactly http://localhost:5173, so Vite must run with `--port 5173 --strictPort` or the API calls fail CORS. Worth a README dev-run note at the end.
- Store contract (set in #8, consumed by #9/#10/#11): quiz store records the chosen ORIGINAL option index per question; score = count where answers[i] === questions[i].correct. Shuffle (#9) stays view-only and translates the clicked shuffled position back to the original index before recording — store/scoring never see shuffle. Keeps data layer unaware of UI reordering (design intent).
- Good pattern (#9): for a view-only shuffle, return an `order[]` map (order[j] = original index at display position j), not just {options, correct}. Translate clicks via order[j] — index math, immune to duplicate option text. Text-based reverse mapping (indexOf(clickedText)) silently mis-grades when two options share a string.
- Vue reactivity (#9): a `computed` re-evaluates only when reactive deps READ during its evaluation change. shuffleQuestion reads only `question`; Math.random is non-reactive and `answers` isn't read, so answering never reshuffles → exactly one stable shuffle per question. This is the idiomatic way to get "compute once per X" stability.
- Vite vue-ts scaffold ships NO test runner. Frontend test tasks must add Vitest + a "test" script themselves. Pure-fn + Pinia-store tests don't need jsdom. Pinia store tests need setActivePinia(createPinia()) in beforeEach, then set store state directly and read getters.
- Process: creating tasks BEFORE the team orphaned them from the team's task list. Net effect was fine (lead briefed each teammate directly with full scope + contracts), but next time create the team first so self-claim works. Manual briefing also let the lead pin cross-teammate contracts (api count param, store answer/score shape) explicitly — which prevented integration drift between parallel backend/frontend chains.
